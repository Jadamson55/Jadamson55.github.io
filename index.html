01 What I build

Data systems that keep working when their sources don't.

Pipelines and lakehouse data

Scheduled ingestion from APIs and files into lake storage and warehouses on AWS (S3, Glue, Athena, Lambda, Redshift) and GCP (BigQuery, Cloud Run, Cloud Functions). Idempotent loads, so a missed or doubled run is harmless.

Data quality, monitoring and anomaly detection

Freshness and failure checks on every source. Last-good fallbacks labeled as such. Flat-line detection that reads a dead sensor as dead, and physical checks like mass balance that catch a wrong answer before it goes out.

P1

AI agent back office

Own project · in daily use

Problem

Requests arrive from a web app and from email at all hours. Each one has to reach the right place, get done, get checked and get a reply. Work stalls silently when a job runs out of time, a machine sleeps or a service hits its usage limit.

Built

  • About 18,000 lines of Python (50 modules). A dispatcher checks the queue every minute and starts one Claude worker per request, up to 8 at once, each with a fixed tool list and a time budget.
  • Leases make sure each job is claimed exactly once across two machines, and a backup takes over when the main one sleeps. A failed job retries once; a job that runs out of time files the rest for a fresh worker under the original request.
  • 19 health checks every 30 minutes fix what's safe and alert a person only when one is needed. Email intake trusts only known senders that pass DKIM and DMARC.
  • Guardrails: workers can't spend money or change infrastructure, and a second AI reviewer checks work before it ships. 495 automated tests. When 7 workers at once hit the usage cap, it learned to pause and requeue instead of failing.

P2

Project app with a 73-tool AI-agent connector

Own project · Google Cloud

Problem

A long construction project produces plans, drawings, decisions, to-dos and site photos that scatter across texts, email and drives. It needed one private place that works from a phone on a weak signal and keeps a locked decision from being quietly undone.

Built

  • A private, phone-first project-management app: FastAPI on Cloud Run, Firestore and private Cloud Storage, with about 23 cloud resources in Terraform, including a budget alert and least-privilege service accounts. It scales to zero when idle.
  • Google sign-in for invited accounts, re-checked on every request. Strict content security policy; files only through the app or one-hour signed links. Uploads go in 8 MB pieces and resume after a dropped signal.
  • Locked decisions are tests: a redraw that breaks one fails the build. Every push runs tests, builds the image, releases to Cloud Run and checks that the app is healthy.
  • A 73-tool MCP connector, with 55 offline tests, lets AI agents read and update projects. Three projects share it. Scale: 110 routes, 51 server-rendered pages, 410 commits in 16 days.

P3

Site data and geology engine

Own project · public federal data

Problem

The facts about a site or a creek are spread across a dozen public services: USGS gauges and lidar, NRCS snow and soil data, NWS forecasts, FEMA flood maps. Each has its own format, limits and outages. Small creeks often have no gauge, and gauges tend to fail in the storms that matter.

Built

  • Ingestion in plain Python from USGS, NRCS, NWS, FEMA and 3DEP: 11 river gauges, 16 snow sites and forecasts for 9 places, batched and cached to stay inside each service's limits.
  • Each source fails on its own: a dead feed is logged, the last good copy is used and labeled as such, and nothing crashes. A flat line on a free-flowing creek is read as a dead gauge, never as "falling". Ungauged creeks are estimated from a neighbor scaled by drainage area, with failover to a backup gauge.
  • Terrain from public 3DEP lidar: a ground model with 1-foot contours that feeds a flood model, joined with USGS geologic maps and NRCS soils. Out come maps, charts and a GIS package (GeoJSON, DXF, KMZ).
  • 86 offline tests on the data modules, many against recorded real responses.

P4

My Animas: river-conditions demo

Personal project · demo

Problem

Flow, water temperature, snowpack and weather alerts for a river live in separate federal feeds on different schedules, and none of them speak plain language.

Built

  • One Cloud Function per source on Cloud Scheduler (USGS every 15 minutes, NWS hourly, NRCS SNOTEL daily), posting to a Django API on Cloud Run with Google-signed ID tokens. One feed failing can't take the others down.
  • Postgres and PostGIS on Cloud SQL with a private IP. Upserts keyed on gauge and time, so a missed or doubled run is harmless. Each function reports its own failures, so feed health tells "failing" from "hasn't run".
  • Plain-language flow levels come from rules, not a model. USGS daily means back to 1980 drive year-over-year charts. React and TypeScript PWA with MapLibre maps; infrastructure in Terraform.

04 How I work with AI

Claude every day. Agents built like infrastructure.

I use Claude daily to draft and test pipeline code, SQL and data-quality checks, and to run agents that do real work. I build those agents the way I build any service: queues, leases, retries, health checks, tests and hard limits on what an agent may do.

Nothing ships on a model's word. It ships when the numbers match a known-good source. When USGS moved its gauge data to new APIs, I queried old and new side by side: flows, the 7-day series and peak records matched exactly before the switch.
